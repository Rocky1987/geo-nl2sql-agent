### 2.2 兩張圖的草稿（S3 依程式碼逐項核對後才定稿）

**架構與請求流程**：

```
瀏覽器（MVC View + Leaflet）
  │ POST /query 或 /query/stream（question、role）
  ▼
QueryController／QueryStreamController ── 每次請求寫一筆稽核（geo_auditor → audit.QueryLog，ledger）
  │
  ▼
Agent（Microsoft Agent Framework，IChatClient → Anthropic 或 Ollama）
  ├─ query_database ──► NL2SQL 管線：提示詞 → 模型 → SqlValidator（AST 白名單）→ geo_reader 執行 → 失敗時有界修正（最多 2 次）
  ├─ get_district_centroid ──► 寫死的參數化 SQL（STCentroid）
  └─ buffer_around_point  ──► 寫死的參數化 SQL（STBuffer）
          │
          └─ GeoJSON 走單次請求的旁路，直接給網頁，不經過模型
admin 角色：同一句已驗證的 SQL 以 geo_reader_pii 重跑，只換表格的值，送往模型的內容不變
```

**安全分層**（由外而內；◆ 確定性，◇ 機率性）：

| 層 | 性質 | 擋什麼 |
|---|---|---|
| 輸入偵測（規則 r1） | ◇ | 明顯的注入語句 |
| 工具結果清理 | ◇ | 資料表內容中的間接注入 |
| SQL AST 白名單 | ◆ | 單一 `SELECT` 以外的一切、白名單外的資料表與函式 |
| 唯讀登入 `geo_reader` | ◆ | 寫入、改結構；個資欄位 `DENY`，只讀得到遮蔽檢視 |
| 逾時與列數上限 | ◆ | 拖垮資料庫的查詢 |
| 輸出防護（金絲雀、40 字元重疊） | ◇ | 提示詞與 schema 逐字洩漏 |
| 稽核（append-only ledger） | ◆ | 事後否認、竄改紀錄 |

格式見 Q2。

### 2.3 Demo 的幾個限制（影響腳本設計）

- **網頁看不到自我修正的過程**：`/query` 與 `/query/stream` 只回最終的 SQL 與結果，沒有每次嘗試的內容。`eval ask` 會印出每次嘗試的 SQL 與失敗原因。
- **雲端模型在 60 題中沒有任何一題被修正救回**（`feasibility-report.md` §11.3）；本機 `qwen2.5:3b` 只有 `G11` 在 M5 救回 3/3，但 2026-10-13 重跑 3 次全失敗（見 §13.2）。
- **本機模型在網頁的 Agent 流程中常不呼叫工具**（§9.5、M6 §12.3 實測 4 題全部如此），所以網頁的場景都要用雲端模型。
- 網頁的 Agent 流程與評估的 NL2SQL 管線提示詞不同，評估裡的失敗題在網頁上不一定以同樣方式失敗，要排練確認。

## 3. 框架版本：固定 .NET 9（Q1 已決定，無 S0）

## 10. 風險與預先決定

| 風險 | 影響 | 預先決定 |

| 排練時某段的結果與暫定不同 | 腳本要換題 | 用 §5 的備案，並在 §13 寫明原因；不為了錄到想要的畫面而改提示詞（K4、K6） |

| 金鑰或個人資訊入鏡 | 金鑰外洩 | 錄影前檢查（§7）；萬一外洩，先到 Anthropic 主控台撤銷金鑰再處理影片 |
| Mermaid 在 GitHub 上顯示不如預期 | 圖看不懂 | S3 推到分支後在 GitHub 上實際檢視再合併 |
| README 越寫越長 | 讀者找不到重點 | 新段落以表格與一句話加連結為主，細節留在 `feasibility-report.md`（Q7） |
