## 1. 目標與驗收

| # | 條件 | 理由 |
|---|---|---|
| K5 | **先凍結再跑**：新增的 30 題、標準 SQL、難度標籤與計分規則，在任何模型看到新題目之前 commit 並打 tag `m5-questions-frozen`。凍結後不改題目文字；標準 SQL 若被證明有錯，只能以勘誤處理（公開前後差異、全部輪次重新計分） | 同一人出題又看結果，最容易不自覺地讓兩者對上（R4）；M1 用的是同樣的規則 |

## 2. 現況與設計

### 2.1 現況（M4 結束時）

- 標準集 `questions.json` 30 題（single 8、join 8、aggregate 7、spatial 7），M1 凍結（tag `m1-questions-frozen`），沒有難度標籤。
- 雲端 `claude-haiku-4-5`（有描述的 schema）在 M1、M2 都是 30/30，**沒有鑑別力**。本機 `qwen2.5:3b` 只在 M1 的 spike 量過（12～13/30，spike 最多修正 1 次、回饋的是資料庫原始錯誤），沒有走過 M2 的管線（最多修正 2 次、錯誤訊息已消毒）。
- `pipeline` 子命令已能逐題跑管線、以執行結果比對、統計驗證器誤擋，結果寫到被 git 忽略的 `Results/`。沒有快取，每次都呼叫模型。
- M4 之後 `geo_reader` 讀不到個資欄位：J04（列出企業客戶姓名）在模型路徑上拿到遮蔽值，M4 S6 回歸 4/5 就是這個原因。
- `Nl2SqlPipeline.MaxCorrections` 是常數 2。

### 2.2 「無自我修正」不另跑：取同一次執行的第 1 次嘗試（Q5）

管線第 1 次送給模型的請求只有 system 訊息與問題，與之後允許修正幾次無關；修正只在第 1 次失敗之後才發生。所以「關掉自我修正的結果」就是「同一次執行中第 1 次嘗試的結果」，不需要另外跑。

- 好處：每一題的有、無修正來自同一個模型回應，是成對比較，差異只來自修正本身；雲端呼叫少約一半；`Core` 不必為了評估把常數改成參數（K6）。
- 依據有測試：`Nl2SqlPipelineTests` 確認第 1 次請求只含 system 訊息與問題（§4.5）。
- 報告寫明這個取得方式（K7）。
- 修正只處理「看得出失敗」的情況（抽不到 SQL、被驗證器拒絕、執行錯誤）。SQL 能執行但結果不對（`wrong_result`）時管線並不知道，不會修正。所以有、無修正的差距上限，是第 1 次嘗試中這三類失敗的題數；報告一起列出。

### 2.3 計分：最終 SQL 以 `geo_reader_pii` 重跑後比對（Q2）

- 管線照產品的條件跑：生成、驗證、以 `geo_reader` 執行、失敗就修正。模型會碰到 M4 的權限（寫 `dbo.Customer` 的個資欄位會被拒），這本身是要量的一部分。
- 管線成功後，把**最終那句已通過驗證的 SQL** 以 `geo_reader_pii` 重跑，用重跑結果與標準答案比對。這和 admin 旁路是同一個做法（M4 計畫 §4.2）。
- 理由：評估量的是「SQL 寫得對不對」。遮蔽是產品刻意加上的轉換，不是 SQL 的錯；不重跑的話，J04 這類題永遠不符，會把「模型寫對了」算成錯。
- 被權限拒絕、三次都失敗的題目照常算錯，並另外計數（錯誤號碼 230）。這也回答 M4 計畫 §11 留下的問題：模型是否習慣寫 `dbo.Customer`。
- `geo_reader_pii` 也是唯讀（M4 S1 已驗證兩層獨立性對它成立），重跑不會改資料。

### 2.4 快取與重現（K4、Q3）

`CachingChatClient` 只在 Eval 使用，包在模型用戶端外面。

- **鍵**：SHA-256（供應商、模型 ID、輪次、完整的訊息內容、溫度、輸出上限）。system 訊息含 schema 說明，所以技術文件 §5.6 說的「題目＋模型＋提示詞版本」自動包含在內；提示詞或 schema 說明一改，鍵就不同，不會誤用舊回應。
- **輪次在鍵裡**：否則第 2、3 輪會直接拿到第 1 輪的回應，變異會被快取強制成 0。
- **值**：回應文字、token 用量、當次實測的呼叫耗時、供應商回報的模型版本。
- **存放**：每個（模型、輪次）一個 JSON Lines 檔（每次實際呼叫後立即附加一行，中斷不會遺失已付費的回應），放在 `eval/results/m5/cache/`。
- **三種模式**：

| 模式 | 行為 | 用途 |
|---|---|---|
| 預設 | 有就用，沒有才呼叫並寫入 | 開發；中斷後重跑不重複付費 |
| `--replay` | 只用快取，缺回應就不寫結果、以錯誤結束並列出缺哪些題；結果寫到 `eval/results/m5-replay/`（不進版控），並與 `m5/` 的正式結果逐題比對 | 沒有金鑰或 Ollama 的人重現公布的數字，保證不花費用 |
| `--fresh` | 忽略既有快取，重新呼叫，結果與新快取寫到 `eval/results/m5-fresh-時間/`（不進版控） | 檢查模型是否已經改變（供應商更新同名模型） |

- **重現的範圍**：`--replay` 重跑的是抽取、驗證、執行、比對與報告；模型回應來自快取，所以準確率與失敗分佈會和公布的數字逐題相同。資料庫仍需以 `seed` 重建（固定種子，內容相同）。
- **勘誤不必重新付費**：標準 SQL 若需勘誤，以 `--replay` 重新計分即可。

### 2.5 延遲（K8、Q6）

- 每題記錄「模型呼叫耗時合計」與「資料庫執行耗時合計」，兩者相加為該題的管線耗時。p50／p95 分別從雲端與本機的正式輪次計算。
- 模型耗時存在快取裡（是當次的實測值），`--replay` 時沿用；資料庫耗時則重新量。所以重現後延遲數字會有小幅差異，準確率不會。
- **不從稽核表算**（M4 計畫原本這樣寫）：評估走 NL2SQL 管線，不經過 `QueryService`；稽核表裡只有在網頁上手動問的請求，樣本不受控。網頁請求另有 Agent 的 1～2 次模型呼叫，實際耗時比這個數字長，README 寫明。

## 3. S1：60 題標準集

### 3.1 組成

- 原 30 題**逐字照抄**（id、類別、問題、標準 SQL、`ordered` 全部相同，由測試鎖住）。`questions.json` 本身不動，M1 的 SHA-256 與 tag 仍然有效。
- 新 30 題，編號接續各類別（S09、J09、A08、G08 起）。
- 每類 15 題：single、join 各新增 7 題，aggregate、spatial 各新增 8 題。
- 新題目刻意偏難，因為原 30 題對雲端沒有鑑別力。目標：新 30 題中「難」至少 15 題、「中」約 10 題、「易」約 5 題。
- 報告一律分開列「原 30 題」與「新 30 題」：原 30 題公開過，雲端在 M1、M2 都全對；新 30 題才是沒有被看過的樣本。

### 3.2 難度規則（出題時標記，凍結前完成）

依標準 SQL 數「特徵」：

| 特徵 | 例子 |
|---|---|
| 每多一張資料表 | 兩表 JOIN 算 1，三表算 2 |
| 分組或分組後篩選 | `GROUP BY`、`HAVING` |
| 子查詢、CTE、`EXISTS`／`NOT EXISTS` | 「從未發生中斷的基地台」 |
| 視窗函式或「每組取前 N」 | `ROW_NUMBER() OVER (PARTITION BY …)` |
| 空間方法 | `STDistance`、`STIntersects`、`STArea` |
| 命名不佳欄位的語意 | `flg1`、`dt2` |
| 日期運算或區間 | `DATEDIFF`、`DATEADD`、季、月份 |
| 比例、百分比或條件彙總 | `SUM(CASE …)`、`100.0 * … / …` |

「易」＝0～1 個特徵；「中」＝2～3 個；「難」＝4 個以上。原 30 題依同一規則補標（只加標籤，不改內容）。

計數細則（S1 出題時定下，凍結前寫入）：

- 資料表以引用次數計：自我 JOIN、子查詢裡的資料表都算（`BaseStation a JOIN BaseStation b` 算 1）。
- 其餘 7 項各最多算 1：`GROUP BY` 加 `HAVING` 算 1；同時有日期區間與日期運算也算 1。
- 「每組取前 N」需要 CTE 或衍生資料表時，視窗函式與子查詢各算 1。
- 不算特徵：單純的 `TOP N`、`DISTINCT`、`ROUND`；人口密度這類除法（「比例」指部分占整體，例如百分比）。
- 結果：原 30 題易 16、中 11、難 3；新 30 題易 5、中 10、難 15。

### 3.3 新題目的方向與限制

方向（避免只出「模型答得對」的題，R4）：

- 口語、間接的說法（「哪幾區的基地台最常斷線？」）；需要把中文對應到英文列舉值（「光纖被挖斷」對應 `FiberCut`）；2～3 題英文或中英混用。
- 反向條件（從未、沒有、除了）、每組取前 N、比例、跨兩個以上關聯的多跳 JOIN。
- 空間結合彙總或 JOIN（例如各區人口密度、距離某區邊界 N 公尺內的他區基地台）。不出質心題：schema 說明已寫明沒有 `STCentroid()`，那是 Agent 工具的工作。

限制（標準答案必須可靠）：

- 不用 `GETDATE()` 等目前時間；日期一律寫在題目裡。
- 結果非空、不超過 200 列（列數上限是 1000，截斷會讓比對失真）。
- 有排序或前 N 的題目，資料中不得有並列造成多種正確答案：出題時以資料庫查第 N 與第 N+1 名確認不同，列在審閱清單；題目寫清楚排序方式，`ordered` 依題意設定。
- 可以讀個資欄位（例如列出姓名），計分以 §2.3 的重跑結果比對。
- 不改 schema 與種子資料。5 座被下毒的基地台名稱照常存在；NL2SQL 管線不把查詢結果交給模型，不影響本評估。

### 3.4 出題流程與凍結（Q1）

1. 起草 30 題與標準 SQL，並標記難度。**過程中不呼叫任何模型**；驗證只靠資料庫與 `pipeline --fake`。
2. 作者逐題審閱：題意是否只有一種合理解讀、標準 SQL 是否真的回答了題目、措辭是否像真實使用者會問的。作者可以改寫措辭（改寫後重新驗證標準 SQL）。審閱清單（含並列與邊界的檢查結果）：`docs/m5-benchmark-review.md`。
3. 通過 §3.5 的測試後，單獨 commit 並打 tag `m5-questions-frozen`。結果檔記錄 `benchmark.json` 的 SHA-256。
4. 凍結之後，才可以對新題目呼叫模型（包含 `--limit 3` 的試跑）。

### 3.5 驗證（S1 的完成條件）

- `Eval/BenchmarkIntegrityTests`（離線）：
  - 60 題、id 不重複、每類 15 題、`difficulty` 只能是 easy／medium／hard。
  - 原 30 題與 `questions.json` 逐欄相同。
  - 標準 SQL 全部通過 `SqlValidator`，且不含 `GETDATE`、`SYSDATETIME`、`CURRENT_TIMESTAMP`、`NEWID`。
- `Database/BenchmarkGoldTests`：每題標準 SQL 以擁有者執行，結果非空、不超過 200 列；以 `geo_reader_pii` 執行的結果與擁有者相同。
- `pipeline --fake "{gold}" --reader pii --questions benchmark.json`：60/60、驗證器誤擋 0。
- 附帶量測（不影響計分）：新 30 題送進 M4 的輸入偵測 r1，照實記錄誤擋數，延伸 M4 的 H7。若有誤擋，只記錄，不改規則。

## 4. S2：計分、快取與 `eval` 子命令

### 4.1 每題記錄的內容

- 第 1 次嘗試與最終結果：是否正確、失敗類型（`no_sql`、`rejected`、`exec_error`、`wrong_result`、`model_error`）。
- 嘗試次數、每次的 SQL 與消毒後的失敗訊息（沿用 `pipeline` 的格式）、驗證器誤擋。
- 被權限拒絕（錯誤 230）的次數。
- 模型呼叫次數、token、模型耗時、資料庫耗時、供應商回報的模型版本。
- **不記錄**查詢結果的資料列，避免把個資寫進公開的結果檔。

### 4.2 每輪結果檔的檔頭

`benchmark.json` 的 SHA-256、system 訊息的 SHA-256（不存原文，可行性報告 §4.3）、`PromptBuilder` 版本（`described`）、`MaxCorrections`、供應商與模型 ID、溫度、輪次、開始時間、快取模式。

### 4.3 `eval` 子命令

```
eval [--models cloud,local] [--runs 3] [--limit N] [--ids S09,J09] [--replay | --fresh]
```

- 預設跑雲端 `claude-haiku-4-5` 與本機 `qwen2.5:3b`（Web 的兩個軌道）各 3 輪，跑完自動執行 `report`。
- 本機模型偶發的 HTTP 錯誤記為 `model_error`：該題算錯、照常進分母，另外計數。這類錯誤（有 HTTP 狀態碼）也寫進快取，`--replay` 才能逐題重現。
- 雲端的模型錯誤，以及本機連不上（沒有狀態碼），都不是量測的一部分：立即停止、不寫快取。排除問題後重跑同一命令，已完成的呼叫由快取接續。

### 4.4 `report` 子命令

只讀結果檔，不呼叫模型、不連資料庫，產生 `eval/results/m5/summary.json`、`summary.md`、`accuracy.svg`（內容見 §6）。

### 4.5 驗證（S2 的完成條件）

- `Eval/CachingChatClientTests`（離線）：相同請求命中；輪次不同不命中；訊息差一個字不命中；`--replay` 缺快取時丟例外並列出題號；命中時回傳存下的用量與耗時。
- `Eval/BenchmarkRunnerTests`（離線，假模型與假執行器）：第 1 次失敗、修正後成功時，「無修正」記錯、「有修正」記對；最終 SQL 以第二個執行器（pii）重跑後才比對；被權限拒絕的次數計算正確。
- `Nl2SqlPipelineTests`：第 1 次請求只含 system 訊息與問題（已有就不補）。
- `pipeline` 的既有輸出格式不變（舊結果檔的欄位都還在）。
- 凍結後，`eval --models cloud --limit 3` 與接著跑的 `eval --replay --models cloud --limit 3` 逐題結果相同。

## 10. 風險與預先決定

| 風險 | 影響 | 預先決定 |
|---|---|---|
| 雲端在新 30 題仍接近滿分 | 主表看不出差異 | 照實報告，結論是「在這個 schema 規模下，雲端模型的瓶頸不在 SQL 生成」。**不在看到結果後追加題目**；要加題就另立新版本的題組與新數字 |
| 出題者無意間避開模型的弱點，或反過來專挑 M1 已知的弱點 | 數字偏高或偏低（R4） | 難度規則、類別配額與題目方向在出題前定好（§3.2、§3.3）；作者審閱；原、新 30 題分開報告 |
| 標準 SQL 有錯 | 準確率被低估或高估 | 凍結前逐題審閱並通過資料庫測試；凍結後發現錯誤以勘誤處理：公開前後差異，以 `--replay` 重新計分全部輪次，不改題目文字 |
| 有排序的題目出現並列 | 正確的 SQL 被判錯 | §3.3 的限制，出題時逐題確認 |
| 同名模型被供應商更新 | 之後重跑的數字不同 | 結果檔記錄供應商回報的模型版本；公布的數字以快取為準，`--fresh` 可以另外量新數字 |
| 本機模型逾時或回 500 | 某些題沒有結果 | 記為 `model_error`，算錯、照常進分母，另列次數 |
| 資料庫偶發逾時（S2 驗證時 `pipeline --fake` 出現過 1 次錯誤 -2，之後 3 次重跑未重現） | 正確的 SQL 被記成 `exec_error`，算到模型頭上 | S3 執行期間不同時跑測試或其他資料庫工作；結果中訊息為逾時的 `exec_error` 逐題檢查，確認是資料庫而非 SQL 造成時，照實在報告中說明 |
| 結果檔夾帶不該公開的內容 | 公開儲存庫外洩（可行性報告 §4.3） | 不存資料列與 system 訊息原文；commit 時由 pre-commit 的 gitleaks 掃描 |
